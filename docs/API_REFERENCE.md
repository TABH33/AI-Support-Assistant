# API Reference

Base URL: `http://localhost:8000` (no `/api` prefix — routers are mounted at
the root; see `backend/app/main.py`). Interactive docs are auto-generated by
FastAPI at `/docs` (Swagger UI) and `/redoc`.

## Auth

Every endpoint below except `POST /auth/login` and `GET /health` requires an
`Authorization: Bearer <token>` header. Tokens are issued by
`POST /auth/login` and carry the caller's `role` (`customer` or
`support_agent`) and, for a `support_agent`, their `access_level`.

**Multi-tenant rule that applies everywhere below**: a `customer`-role
caller is always scoped to their own `customer_id`, derived from the JWT —
never from anything in the request body or query string. A `support_agent`
caller is unrestricted (can see/act across every customer) and, on
endpoints that need a customer context, must supply `customer_id` explicitly
since they have no fleet of their own. A customer-scoped resource that
exists but belongs to a different customer returns `404`, not `403` — the
API never reveals that something exists but isn't yours.

---

### `GET /health`

No auth. Returns `{"status": "ok"}`.

---

### `POST /auth/login`

No auth required (this *is* the auth endpoint).

**Request**
```json
{ "email": "customer-01@example.test", "password": "..." }
```

**Response** `200`
```json
{ "access_token": "...", "token_type": "bearer", "role": "customer", "access_level": null }
```

Checked against `Customer` first, then `SupportAgent`, by email. Any
failure (unknown email, wrong password, on either table) returns the same
`401` with a generic message — the API never reveals which half was wrong.

## Telematics (`backend/app/api/telematics.py`)

All read-only. All require `require_role("customer", "support_agent")`.

| Method | Path | Notes |
|---|---|---|
| `GET` | `/drivers` | List drivers in caller's scope |
| `GET` | `/drivers/{driver_id}` | 404 if not found or not owned |
| `GET` | `/vehicles` | List vehicles in caller's scope |
| `GET` | `/trips` | Optional `?driver_id=` / `?vehicle_id=` filters |
| `GET` | `/trips/{trip_id}/events` | Driving events for one trip; 404 if trip not visible |
| `GET` | `/devices` | Optional `?customer_id=` (support_agent only — ignored for customer callers) |

Scoping per entity: `Device`/`Driver`/`Vehicle` filter directly on their own
`customer_id` column; `Trip` and `DrivingEvent` have no `customer_id` column
of their own and are scoped transitively (`Trip` via its `Driver`,
`DrivingEvent` via its parent `Trip`).

**Response shapes** (`DriverOut`, `VehicleOut`, `TripOut`, `DrivingEventOut`,
`DeviceOut`) mirror their ORM models field-for-field — see
[DATA_MODEL.md](DATA_MODEL.md).

## Chat (`backend/app/api/chat.py`)

All require `require_role("customer", "support_agent")`.

### `POST /chat`

The main RAG chat endpoint. See [RAG_PIPELINE.md](RAG_PIPELINE.md) for what
happens inside.

**Request** (`ChatRequest`)
```json
{
  "session_id": null,
  "query": "why is device X offline?",
  "driver_id": null,
  "trip_id": null,
  "vehicle_id": null,
  "device_id": 1,
  "customer_id": null
}
```

- `session_id` — reuse an existing session if given; otherwise a new one is
  created (requires `device_id`, and for a `support_agent` caller,
  `customer_id`).
- `driver_id` / `trip_id` / `vehicle_id` — optional context hints for
  retrieval. Client-supplied, but **never trusted for tenant scoping** —
  the `customer_id` actually used for data access always comes from the
  resolved `ChatSession`, not from the request.
- `device_id` — required only when starting a new session; must belong to
  the resolved `customer_id` or the call 404s.
- `customer_id` — only honored for a `support_agent` starting a new
  session.

**Response** (`ChatResponse`) `200`
```json
{
  "session_id": 1, "message_id": 42, "answer": "...",
  "confidence": 0.82, "escalated": false,
  "route_plan": null
}
```

Before the RAG pipeline runs, the query is checked for two other intents,
in order:

1. **Route planning** — "plan a trip from Sydney CBD to Parramatta" routes
   to the [route-planning feature](ROUTE_PLANNING.md) instead of RAG,
   returning `confidence: 1.0, escalated: false` and a populated
   `route_plan` field (same shape as [`POST /route-plan`](#post-route-plan)'s
   response) on success — `null` on every other kind of turn.
2. **Reports** (see [RAG_PIPELINE.md](RAG_PIPELINE.md)) — phrases like
   "daily report" or "start of day" route straight to the report
   generators instead, also returning `confidence: 1.0, escalated: false`
   unconditionally.

### `GET /tickets`

List `SupportTicket` rows in the caller's scope. `support_agent` may narrow
with `?customer_id=`.

### `GET /notifications`

List `Notification` rows in the caller's scope. Same `?customer_id=` rule.

### `PATCH /chat/messages/{chat_message_id}/feedback`

Thumbs up/down on an assistant `ChatMessage`.

**Request**
```json
{ "feedback": false }
```

**Response** `200`
```json
{ "chat_message_id": 42, "feedback": false, "escalated": true, "support_ticket_id": 7 }
```

- `feedback: false` (thumbs-down) creates a `SupportTicket` — idempotently:
  pressing thumbs-down twice, or thumbs-down on a session already
  auto-escalated for low confidence, reuses the existing ticket rather than
  erroring (`ChatSession 1 → 0..1 SupportTicket` is a DB unique constraint).
- `feedback: true` (thumbs-up) never escalates; `escalated` is always
  `false` and `support_ticket_id` always `null`.
- 400 if the target message's `role` isn't `assistant` — there's no
  feedback concept on a user's own message.

### `POST /chat/sessions/{chat_session_id}/survey`

Post-resolution Customer Effort Score (CES-7 scale).

**Request**
```json
{ "score": 3 }
```
`score` must be 1–7 (422 otherwise).

**Response** `200`
```json
{ "chat_session_id": 1, "ces_score": 3 }
```

## Reports (`backend/app/api/reports.py`)

Manual triggers for the same report generators the chat pipeline can route
into. No scheduler exists in this codebase — `app.ai.reports`'s
`generate_start_of_day_report`/`generate_end_of_day_report` are plain
`(customer_id, *, db)` functions a future cron job could call directly.

### `POST /reports/start-of-day` / `POST /reports/end-of-day`

**Request** (`ReportRequest`, body optional)
```json
{ "customer_id": null }
```
Ignored for a `customer`-role caller (always their own id); **required**
(400 if omitted) for a `support_agent`.

**Response** (`ReportResponse`) `200`
```json
{ "customer_id": 1, "report": "**Fleet Summary Report...**" }
```

Every report call is written to `audit_logs` (`action=report_generated`),
same as a chat answer.

## Route Planning (`backend/app/api/route_plan.py`)

Full detail (algorithm, warning thresholds, known limitations): [ROUTE_PLANNING.md](ROUTE_PLANNING.md).

### `POST /route-plan`

Requires `require_role("customer", "support_agent")`. No `customer_id`
scoping — route/weather/risk-zone data isn't customer-owned.

**Request** (`RoutePlanRequest`)
```json
{ "origin": "Sydney CBD", "destination": "Parramatta", "waypoints": null }
```
`origin`/`destination`/each `waypoints` entry accept either a place-name
string (geocoded server-side via OpenRouteService) or
`{"lat": ..., "lon": ...}`.

**Response** (`RoutePlanResponse`) `200` — **always 200**, even on failure;
failures are reported in-band via `unavailable`/`unavailable_reason`, never
a 5xx:
```json
{
  "distance_km": 24.14,
  "duration_min": 27.6,
  "geometry": { "type": "LineString", "coordinates": [[151.21, -33.87], ...] },
  "warnings": [
    {
      "location": { "lat": -33.84, "lon": 151.02 },
      "distance_from_origin_km": 12.1,
      "type": "risk_zone",
      "severity": "moderate",
      "description": "11 driving events recorded within 500m of this point (7 harsh braking)."
    }
  ],
  "unavailable": false,
  "unavailable_reason": null,
  "unavailable_message": null
}
```

On failure, `distance_km`/`duration_min`/`geometry` are `null`, `warnings`
is `[]`, `unavailable` is `true`, and `unavailable_reason` is one of:

| `unavailable_reason` | Meaning |
|---|---|
| `"geocoding_failed"` | A place name didn't resolve — `unavailable_message` names it and suggests checking spelling |
| `"service_unavailable"` | ORS/Open-Meteo outage, missing `ORS_API_KEY`, or a database error — `unavailable_message` suggests retrying shortly |

Every call (success or failure) is written to `audit_logs`
(`action=route_plan_generated`), noting origin/destination and the outcome.
